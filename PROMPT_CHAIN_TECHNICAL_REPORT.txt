EXECUTIVE SUMMARY
-----------------

Pitch Synthase is not a one-shot “make me a deck” prompt. It is an
argument-compilation and visual-production workflow whose central design
problem is authority management:

    What may be said?
    Which source wins when two inputs disagree?
    Where may the model reconstruct missing commercial context?
    Which decisions must remain identical across independently sampled slides?
    Which defects justify paying for another image generation?

The current system separates those questions into three planes:

1.  The inference control plane decides which pitch domains are SOURCE-bound,
    may be INFERred, or must be OMITted.
2.  The generation plane converts the source packet into a strategic approach,
    narrative anchor, typed visual grammar, ordered storyboard, and independent
    full-bleed slide images.
3.  The verification plane audits spelling, factual authority, and diagram
    semantics independently, then spends another image call only when a
    concrete correction exists.

This separation is the architecture. The models are capable, but model quality
alone cannot guarantee lossless source transport, cross-slide consistency,
single-title ownership, or fault isolation. Pitch Synthase moves those
properties into explicit contracts and code-level handoffs wherever possible.


HOW TO READ THE CLAIMS IN THIS REPORT
-------------------------------------

The report uses four evidence labels:

    CODE-ENFORCED
        A deterministic check, schema, state transition, or byte-identical
        splice implements the behavior.

    PROMPT-ENFORCED
        The behavior is explicitly specified to a model, but no deterministic
        postcondition proves that every output obeys it.

    LIVE-VALIDATED
        The behavior has been observed on real API calls in this workshop.

    CONTRACT-VALIDATED
        Inputs, propagation, and prompt construction have been inspected or
        exercised locally, but the newest combination has not been subjected
        to a complete fresh model run.

These labels matter because “the prompt says so” is not the same kind of
guarantee as “the worker rejects any output that violates it.”


1. CURRENT EXTERNAL INPUT CONTRACT
----------------------------------

The canonical machine-readable input surface is
ps_test_input.schema.json, version 1.6.0.

Required founder inputs:

    test_name
        Bookkeeping only. It is not sent to a model.

    audience
        The people the pitch must persuade. This is part of the factual intent
        of the pitch and is not an optional content category.

    elevator_pitch
        The original founder narrative: problem, mechanism, proposition, and
        any facts supplied directly by the user. This is primary source
        material, not a summary field.

    conveys
        The impressions the presentation must leave: strategic posture,
        credibility target, category framing, and desired audience response.

    target_stage
        approaches | single_slide_previews | full_deck | finalized

Optional source and control inputs:

    doc_text
        Supporting specification, outline, whitepaper excerpt, or other raw
        source text. It is transported verbatim rather than pre-summarized.

    supporting_image_path
        Product mockup or other reference image. It becomes direct multimodal
        evidence at the paid Anchor Writer and Deck Builder stages.

    archetype_id
        One of ten founder-posture archetypes, or null for automatic selection.

    approach_id
        The selected one of four drafted approaches for full-deck generation.

    slide_count
        Requested CONTENT slides, 4–24. The worker passes slide_count + 1 to the
        Deck Builder so the complete output contains exactly one title slide.

    universal_refinement_instruction
        A deck-wide user instruction applied during finalization.

    pitch_aspect_modes
        Six independent OMIT / INFER / SOURCE controls, default INFER.

    excepted_inference_elements
        Narrow permissions inside the senior Pitch Aspect policy. Current
        supported values: pricing and mockup_prototype_design.

    inferred_element_decisions
        Per-element review decisions used immediately before finalization.

The six Pitch Aspects are:

    customer_stakeholder_value
    market_ecosystem_competition
    commercialization_pricing_financial
    proof_validation_defensibility
    execution_team_risk
    transaction_ask_use_of_proceeds

There is deliberately no aspect control for visual layout or presentation
quality. Those are baseline responsibilities of the product, not optional
pitch content.

Representative current input:

{
  "test_name": "vitriflux_full_deck",
  "audience": "Deep-tech investors, AI hardware companies, data-center operators",
  "elevator_pitch": "<verbatim founder narrative>",
  "conveys": "A category change, a credible retrofit entry point, and a platform",
  "doc_text": "<verbatim concept specification>",
  "supporting_image_path": "/absolute/path/to/reference.png",
  "archetype_id": "arch_davinci",
  "target_stage": "full_deck",
  "approach_id": "approach_1",
  "slide_count": 13,
  "pitch_aspect_modes": {
    "customer_stakeholder_value": "INFER",
    "market_ecosystem_competition": "INFER",
    "commercialization_pricing_financial": "INFER",
    "proof_validation_defensibility": "SOURCE",
    "execution_team_risk": "SOURCE",
    "transaction_ask_use_of_proceeds": "OMIT"
  },
  "excepted_inference_elements": [],
  "inferred_element_decisions": {}
}

With slide_count 13, this contract requests a 14-slide presentation: one cover
plus thirteen content slides. This translation is CODE-ENFORCED.

Workshop tooling note: ps_test_input.schema.json defines all four target-stage
values, while run_ps_test_input.py currently dispatches only the approaches
stage. Full-deck and finalization tests use dedicated workshop scripts. This is
a small dispatcher hookup still absent from the generic test runner, not a
pipeline limitation or a proposed product feature.


2. AUTHORITY MODEL
------------------

The most consequential improvement in the current system is that narrative
framing and factual transport are no longer the same operation.

For any included aspect, authority is resolved in this order:

1.  OMIT is a denial rule. If an aspect is OMIT, it is excluded even when the
    source contains it.
2.  A user refinement that directly settles a fact is a canon override for
    every slide touching that fact.
3.  Raw founder narrative, supporting document, and reference image are the
    primary factual authority.
4.  Under INFER, a source-silent concrete detail may be reconstructed. Its
    earliest storyboard occurrence becomes deck-wide canon.
5.  A narrow authorized inference such as pricing may establish one explicit
    proposed value only when its senior Pitch Aspect is also INFER.
6.  The Anchor Writer governs framing, pressure, audience logic, and narrative
    posture. It does not supersede the source.
7.  Archetype and selected approach govern rhetorical strategy.
8.  Template or preview images govern surface styling only.

This is not merely prose in one large prompt. The worker sends the raw source
packet to the Deck Builder independently of the Anchor Writer output. The
packet begins:

    “The pitch content was based on the following user-provided materials.”

It then includes separate, verbatim sections for:

    FOUNDER NARRATIVE / ORIGINAL PITCH
    SUPPORTING SPECIFICATION / SOURCE DOCUMENT

The accompanying instruction preserves source-backed names, quantities, units,
ranges, statuses, caveats, development targets, and phase gates, and explicitly
forbids converting a target or hypothesis into a validated result.

CODE-ENFORCED property:
    The raw text crosses the Anchor Writer → Deck Builder seam independently.

PROMPT-ENFORCED property:
    The Deck Builder uses that text faithfully and at the right rhetorical
    moments.

The user-provided image is also attached directly to Deck Builder calls as
“AUTHORITATIVE VISUAL SOURCE MATERIAL.” It can inform depicted form, parts,
materials, and relationships without being treated as a style template or
copied verbatim.


3. THE PITCH ASPECT CONTROL PLANE
---------------------------------

Each of the six optional pitch domains has one of three states:

SOURCE
    Direct claims, examples, names, numbers, and values must come from user
    material. Missing details are omitted rather than reconstructed.

INFER
    The deck may combine source-backed facts with plausible reconstructed
    context. The source wins on conflict. A reconstructed concrete detail
    becomes deck-wide canon at first use.

OMIT
    No direct claim, example, number, named instance, diagram, or substantive
    content from that domain may appear.

All six default to INFER. The defaults make Pitch Synthase capable of producing
a complete pitch from sparse source material, while the independent states let
the same pipeline produce deliberately narrow presentations—for example, a
pure technical-validation deck with commercialization and transaction content
omitted.

The worker compiles the six values into one grouped Deck Builder briefing:

    The pitch purely reflected the source material for: <SOURCE aspects>.

    The pitch also included details that may or may not be in the source
    material for: <INFER aspects>.

    The pitch specifically excluded: <OMIT aspects>; generic fluff;
    pointless repetition; typographical errors.

Empty SOURCE or INFER clauses are absent. The OMIT clause is always present,
even if the user chose no OMIT aspects, because the three quality exclusions
are always-on requirements in the implemented Deck Builder briefing. This
compiled briefing is added by the worker at the Deck Builder seam; it does not
leak into upstream user-facing terminology or the refinement policy.

The same normalized mode map crosses the finalization seam:

    INFER
        Source silence is not an error. Source conflicts are errors. When the
        source is silent, later storyboard uses are compared against the
        earliest occurrence.

    SOURCE
        Unsupported direct content must be replaced from source or removed.

    OMIT
        Any substantive presence is actionable and must be removed.

The source verifier receives the complete ordered storyboard so that INFER
consistency can be evaluated across slides rather than one image in isolation.
The judge receives the same policy. Regeneration is wrapped by the same
Deck Builder input constructor, so a correction call does not silently lose
the aspect policy or source packet.

Important guarantee boundary:

    The mode normalization and propagation are CODE-ENFORCED.
    First-use consistency is PROMPT-ENFORCED; there is not yet a typed,
    deterministic deck-wide fact registry.


4. CURRENT WORKER PIPELINE
--------------------------

The active full-pitch-first path is:

    intake
      ↓
    pitch quality gate ───────→ optional pitch elaborator
      ↓
    approach drafter
      ↓
    optional targeted approach regeneration
      ↓
    optional one-slide previews
      ↓ user selects one approach
    Anchor Writer
      ↓
    Deck Builder: visual grammar + authorized inferences + N+1 storyboard
      ↓
    per-slide image generation
      ↓
    awaiting review
      ↓
    per-slide verification DAG
      ↓
    PDF + PPTX + HTML + Markdown + PNGs + acceptance manifest


4.1 PITCH QUALITY GATE

Worker:
    pitch_quality_gate_worker

Model:
    gpt-5.4 by default through QUALITY_MODEL

Purpose:
    Decide whether the input contains a real pitch with enough mechanism and
    intent to support four distinct approaches.

Output:
    is_real_pitch, reason, missing_elements

This is a diagnostic text call. It does not silently rewrite the founder's
source material.


4.2 OPTIONAL PITCH ELABORATOR

Worker:
    pitch_elaborator_worker

Purpose:
    Ghostwrite a more complete founder draft when explicitly requested.

Output:
    is_nonsense, elevator_pitch, invented_elements, conveys_suggestion,
    reason_for_placeholder

The returned draft is not automatically persisted over the user's original
pitch. Acceptance remains an explicit product decision.


4.3 APPROACH DRAFTER

Worker:
    approach_drafter_worker

Model:
    gpt-5.4

Input:
    founder pitch, audience, desired impressions, optional source text,
    and either a fixed archetype or the ten-entry archetype catalog.

Output:
    exactly one archetype and four approaches:

        approach_id
        label
        pitch_angle
        key_differentiator
        visual_direction

The validator requires exactly approach_1 through approach_4, in order,
non-empty required fields, and labels unique within the batch.

No images are required for this stage. It is intentionally cheap enough to
explore strategic alternatives before committing to a full render.


4.4 TARGETED APPROACH REGENERATION

Worker:
    approach_regenerate_worker

The worker regenerates only selected approach IDs and gives the model the kept
approaches as negative-space context. This preserves user progress and reduces
the probability that a replacement merely renames an existing strategy.


4.5 SINGLE-SLIDE PREVIEW

Worker:
    single_slide_preview_worker

Per selected approach:
    one text call produces a slide draft
    one image call renders it

The preview is an aesthetic and strategic audition, not the first slide of the
eventual paid deck. Early approach exploration remains text-led; the original
supporting image becomes direct multimodal evidence at paid generation.


4.6 ANCHOR WRITER

Worker phase:
    generation_worker → paid_anchor_writer

Model:
    gpt-5.4

The Anchor Writer reconstructs the latent presentation in which this pitch
would have succeeded. It establishes audience pressure, rhetorical posture,
and a deck_generation_prompt. Its output contract is:

{
  "user_inputs": { ... },
  "deck_generation_prompt": "..."
}

It does not own slide copy, page count, visual grammar, or factual authority.
The supporting image is attached to its multimodal input, but the raw source is
also transported independently to the next worker. This prevents a compressed
anchor narrative from becoming a lossy bottleneck for all downstream content.


4.7 DECK BUILDER

Worker phase:
    generation_worker → paid_storyboard

Model:
    gpt-5.4

The Deck Builder receives a multipart user message assembled by
_deck_drafter_input:

1.  Anchor payload:
        original Anchor Writer JSON
        focused Deck Builder instruction
        optional slide number for per-slide rendering

2.  Authoritative source packet:
        verbatim elevator_pitch
        verbatim doc_text

3.  Compiled Pitch Aspect worker briefing.

4.  Archetype, selected approach, and visual-direction context.

5.  Selected template or preview-slide images when applicable.

6.  User-provided product/reference image as independent visual evidence.

Its storyboard response contains:

    visual_grammar
        One typed style object selected once for the deck.

    authorized_inferences
        Optional, narrow, deck-wide decisions for explicitly permitted
        inference elements.

    storyboard
        Exactly N+1 ordered slide records containing slide_number, title,
        purpose, style_tags, and image_prompt.

The worker rejects:

    an incorrect storyboard length
    non-sequential slide numbers
    any storyboard item with an empty image_prompt

Title ownership is explicit:

    Slide 1 is the one and only title/hero cover.
    Slides 2 through N+1 carry the argument.
    No separate hero image call is made by the current generation worker.
    No slide-number or pagination chrome is requested.


4.8 STRUCTURED VISUAL GRAMMAR

The visual grammar is selected once and spliced byte-identical into every
slide prompt by format_visual_grammar_block. Its fields govern:

    background
    foreground
    accent
    typography
    diagram_style
    panel_style
    grid_system
    line_weight

This turns visual consistency from “please remember the style” into a shared
prompt artifact controlled by code. It does not make independent image samples
pixel-identical, but it removes model-authored paraphrase as a source of
style drift.


4.9 PER-SLIDE IMAGE GENERATION

Worker phase:
    generation_worker → paid_slide_<N>

Tool:
    Responses API image_generation using gpt-image-2

Current parameters:

    size             2048x1152
    quality          medium
    output_format    png
    background       opaque
    partial_images   0

Every completed slide is its own image call. The system consumes only the final
image. partial_images is explicitly zero so a future SDK or model default
cannot begin returning unused intermediate images.

Concurrency and throughput are distinct controls:

    _chunked_gather default concurrency: 4
    process-wide image budget: 20 calls per rolling 60 seconds

The rolling-window limiter is protected by an asyncio lock and shared by all
jobs in the process. Concurrency limits simultaneous work; the limiter controls
aggregate image starts over time.

Each slide gets two attempts. The deck fails only when more than two slides
remain failed after retry; otherwise the usable set advances to review.


5. THE REFINEMENT DAG
---------------------

Current finalization worker:
    verification_worker

The older finalization_worker and its single large batch refiner remain in the
repository for reference, but they are not the current mechanism.

For each numbered slide:

                         ┌─ spelling verifier ─┐
    proof image + intent ├─ source verifier ───┼─ code fan-in ─ judge
                         └─ diagram verifier ──┘                 │
                                                                ├─ pass:
                                                                │  copy proof
                                                                └─ regenerate:
                                                                   one image call

Slides are processed in bounded groups of six. Within a slide, the three
specialist verifier calls run concurrently.

Verifier responsibilities are deliberately narrow:

    spelling
        Visible orthography and malformed text.

    source accuracy
        Authority, source conflicts, mode semantics, authorized inference,
        user canon overrides, and cross-slide consistency.

    diagram accuracy
        Whether arrows, charts, labels, icons, proportions, and depicted
        relationships agree with the slide's stated intent.

Fan-in is ordinary Python list concatenation. No synthesis model call can lose
or reinterpret findings before the disposition step.

Each verifier emits structured issues with an actionable boolean. The judge
does not parse prose to rediscover materiality:

    zero actionable issues  → pass
    one or more actionable  → regenerate

Non-actionable uncertainty remains visible in verification_report.json but
cannot trigger spend by itself.

Regeneration is text-to-image, not image-to-image. The worker takes:

    the original verbatim image_prompt
    the same byte-identical visual_grammar
    judge-authored corrective_constraints
    the same Anchor payload
    the same raw source packet
    the same Pitch Aspect briefing
    the same visual references

This is a controlled re-sampling of the original specification, not a new
creative brief written from memory.


6. NARROW AUTHORIZED INFERENCE
------------------------------

Pitch Aspect modes answer whether an entire content domain may be sourced,
reconstructed, or excluded. excepted_inference_elements answers a narrower
question inside an INFER domain.

pricing
    Allows the Deck Builder to propose one explicit amount, tier, package,
    licensing fee, and related unit-economic structure when the source is
    silent. It does not control whether commercialization strategy, industry
    economics, or business-model logic may appear. Without the permission, the
    system may still construct a commercialization strategy; it simply cannot
    invent the amount the pitch company charges.

mockup_prototype_design
    Allows one proposed visual and interaction system. It does not authorize
    unsupported product, customer, traction, or financial claims.

Pitch Aspect modes are senior. A narrow pricing permission cannot reopen a
commercialization aspect marked SOURCE or OMIT.

The Deck Builder decides each authorized value once in authorized_inferences.
The source verifier then treats that value as deck-wide canon unless a user
edit supersedes it.

Before finalization, inferred_element_decisions supports three guarded paths:

    unchecked
        Keep the consistent inferred value and describe it as proposed.

    checked with no replacement edit
        Hard-block before any verifier, judge, or image spend.

    checked with a covering edit
        Treat the user's replacement as canon and remove inference-disclosure
        wording after correction.

    checked with a non-covering edit
        Drop the affected slide from concatenated deliverables rather than
        ship an unresolved claim. The original proof remains in the archive.


7. STATE, IDEMPOTENCY, AND TELEMETRY
-----------------------------------

SQLite stores one jobs row per deck lifecycle. JSON fields include:

    approach_candidates_json
    deck_proof_plan
    slide_specs
    reviewed_slides
    telemetry_context_json
    excepted_inference_elements
    inferred_element_decisions
    pitch_aspect_modes

Mutating workers use claim_job_status as an atomic compare-and-set. Duplicate
dispatch against a job that has already advanced does not run the stage twice.

The principal active status path is:

    created
      → approaches_running
      → approaches_ready
      → paid
      → generating_plan
      → plan_ready
      → rendering_slides
      → awaiting_review
      → finalizing
      → complete

Failure statuses and several legacy/template-first statuses remain for
compatibility and experimental paths.

All model traffic passes through _responses_create, which records model,
stage, usage, output path, errors, and workflow events to:

    <job>/telemetry/events.jsonl
    <job>/telemetry/summary.json

The wrapper also attempts PostHog generation capture. This provides an
inspectable local trace even when external analytics are unavailable.

10. GUARANTEES AND NON-GUARANTEES
---------------------------------

Current code-level guarantees:

    exactly four validated approach records
    requested content count becomes one N+1 storyboard
    exactly one Deck Builder-owned title position
    sequential storyboard slide numbers
    non-empty per-slide image prompts
    one shared visual grammar spliced into every image prompt
    raw founder narrative and source document cross the anchor seam
    supporting image reaches paid multimodal stages
    Pitch Aspect modes are normalized and propagated
    partial image generation is disabled
    process-wide 20-per-minute image throttling
    per-slide verification fault isolation
    no regeneration spend for a clean slide
    atomic job-stage claims
    manifest validation before completion

Prompt-level guarantees that remain probabilistic:

    source facts appear on the most persuasive slides
    a model never produces title-like visual repetition after slide 1
    reconstructed INFER values remain perfectly consistent
    an OMIT concept is never implied indirectly
    regenerated slides preserve exact composition
    generated image text is perfectly legible
    a verifier notices every defect visible in a raster image

The report intentionally does not collapse those two classes.

This distinction replaces the previous report's overbroad claim that every
documented mechanism had been live-tested.


12. CURRENT LIMITS AND WORKSHOP WIRING
--------------------------------------

1.  Cross-slide INFER canon is represented in the storyboard and enforced by
    model comparison, not by a typed fact ledger with deterministic equality
    checks. That is the current guarantee boundary, not a claim that the
    product must always work this way.

2.  Approach labels are unique inside one four-approach response, not across
    separate runs.

3.  Fresh text-to-image regeneration can preserve the specification while
    shifting composition. Exact pixel continuity is not guaranteed.

4.  Raster verification has an evidence ceiling. It can compare visible text
    to source but cannot reliably recover malformed tiny text that no model can
    read with confidence.

5.  This workshop is isolated. None of these mechanisms should be described as
    current production behavior until an explicit integration and production
    validation pass occurs.

Two current setup items are intentionally not listed as system limits:

    run_ps_test_input.py needs a straightforward dispatch hookup for the three
    target stages that currently use dedicated scripts.

    the workshop virtual environment needs its declared python-pptx package for
    clean-environment PowerPoint export.


13. END-TO-END PSEUDOCODE
-------------------------

    job = persist(raw_user_input)
    modes = normalize_pitch_aspect_modes(job.pitch_aspect_modes)

    if requested:
        gate = quality_gate(job.elevator_pitch)
        draft = optional_elaborator(job.elevator_pitch)

    approaches = validate_exactly_four(
        approach_drafter(job.source, job.audience, job.conveys, archetype)
    )
    selected = user_selects(approaches)

    content_count = validate_4_to_24(job.slide_count)
    total_count = content_count + 1

    anchor = anchor_writer(
        source_summary_context,
        audience,
        selected,
        supporting_image
    )

    builder_input = [
        anchor,
        verbatim_founder_narrative,
        verbatim_supporting_document,
        compile_aspect_briefing(modes),
        selected_approach_and_archetype,
        style_references,
        authoritative_supporting_image
    ]

    schema = deck_builder(builder_input, total_count)
    assert len(schema.storyboard) == total_count
    assert schema.slide_numbers == range(1, total_count + 1)

    for slide in bounded_batches(schema.storyboard, concurrency=4):
        await process_wide_image_budget(20, per_seconds=60)
        proof = image_generate(
            original_prompt=slide.image_prompt,
            shared_visual_grammar=schema.visual_grammar,
            partial_images=0
        )

    for slide in bounded_batches(proofs, concurrency=6):
        spelling, source, diagram = await parallel_verify(
            slide,
            modes,
            complete_storyboard,
            source_packet,
            canon_overrides,
            authorized_inferences
        )
        disposition = judge(actionable_issues_only)

        if disposition == "pass":
            final = proof
        else:
            final = image_generate(
                original_prompt,
                shared_visual_grammar,
                disposition.corrective_constraints,
                same_builder_input
            )

    build_and_validate_exports(final_slides, verification_report)


BOTTOM LINE
-----------

Pitch Synthase’s differentiator is not that it invokes a language model and an
image model in sequence. Its differentiator is that it compiles user intent
into explicit authority, inference, narrative, visual, and verification
contracts—and preserves those contracts across worker boundaries that would
otherwise become information-loss points.

The substantive remaining guarantee gap is deterministic fact canon: inferred
values are checked through the complete storyboard, but they are not yet stored
in a typed ledger that code can compare without model judgment. The generic
runner and local PPTX package are just wiring. Production integration is a
separate deployment decision.
